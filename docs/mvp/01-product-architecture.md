# 01 — Final product architecture

## 1. The decision everything else follows from

**Hive is the source of truth. Firestore is a replication target.**

Every write in the application takes the same three steps, in this order:

```
1. write to Hive          synchronous, always succeeds, IS the commit
2. enqueue in the outbox  durable intent to replicate
3. attempt Firestore      best effort; failure is not the user's problem
```

Reads come from Hive only. No screen waits on a network call, and no screen
shows a spinner for data the device already has.

This is implemented once, in `SyncedCollection<T>`
(`app/lib/core/data/synced_collection.dart`), and every feature repository
composes one rather than reimplementing the pattern. There is exactly one
place where the offline guarantee can be got wrong.

The consequence is that a gym basement, a plane, and a dead SIM are all
ordinary operating conditions rather than error states. The offline banner
says "Offline · everything still works" because that is literally true.

## 2. Layers

```
presentation   Flutter widgets + Riverpod providers
      │        knows about: domain, other presentation
      ▼
data           repositories, SyncedCollection, platform services
      │        knows about: domain, core
      ▼
domain         entities, value objects, engines — PURE DART
               knows about: nothing. No Flutter. No Firebase.
```

The domain layer's purity is enforced mechanically by
`app/tool/check_sources.py`, which fails CI if a domain file imports Flutter or
Firebase. That rule is what makes the engines exhaustively testable and what
allowed the same formulas to be mirrored in TypeScript and bound to shared
fixtures.

## 4. Engines

Four pure functions produce every number the user sees:

| Engine | Produces | Version |
|---|---|---|
| `MacroCalculator` | BMR, TDEE, training/rest-day targets, protein floor, water | `macro-1.0.0` |
| `RecoveryEngine` | recovery score, band, training action | `recovery-1.0.0` |
| `E1rmCalculator` + `PrDetector` | estimated 1RM, personal records | `e1rm-1.0.0` |
| `LoadEngine` | progression suggestions | `load-1.0.0` |

They are versioned, deterministic, dependency-free, and executed against
golden fixtures in `test/fixtures/engines/` that are **also executed by the
TypeScript implementation** in `functions/`. A divergence fails both builds.
The fixtures themselves are generated by a third, independent implementation
in `tool/generate_engine_fixtures.py`: agreement between three implementations
written against the specification is much stronger evidence than agreement
between two.

Nothing derived is stored. Personal records are recomputed from sessions on
demand, so deleting the session that produced a record removes the record —
the only self-consistent behaviour. Macro targets are derived from the profile,
so editing a bodyweight cannot leave a stale calorie goal behind.

## 5. State management

Riverpod 2.6, hand-written providers, no code generation.

- `bootstrapProvider` is injected in `main()` via a `ProviderScope` override
  and throws if read before that. Nothing in the widget tree awaits
  initialisation, and no provider models "not ready yet" as a state.
- Every user-scoped repository depends on `currentUidProvider`, so a sign-out
  tears down and rebuilds the entire data layer automatically.
- `SettingsController` captures its dependencies in `build()` and never calls
  `ref.read` after an await — a notifier that writes to something it also
  watches will otherwise throw the moment its own write lands.

## 6. Navigation

GoRouter 14.6 with a `redirect` and a `refreshListenable` bridged from
Riverpod. The redirect is the single place that answers "where does this user
belong?":

```
auth still loading            → /            (splash; never flash sign-in
                                              at a user who is signed in)
signed out                    → /welcome
signed in, not onboarded      → /onboarding
signed in, onboarded, on auth → /home
```

A `ShellRoute` carries the five-destination bottom bar; focused tasks
(add food, live workout, editors) are full-screen routes, because a bottom bar
during a task is an invitation to abandon it.

## 7. Local storage

Hive, AES-encrypted, with the key held in the Android Keystore via
`flutter_secure_storage`. Eighteen boxes, one per record type plus `outbox`
and `meta`.

Values are stored as **JSON strings**, not through generated TypeAdapters.
That choice costs a little encode/decode time and buys three things: the same
bytes go to Hive and to Firestore, so the two stores can never disagree about
a type; there is no code generation step; and a schema change is a `fromJson`
edit rather than a migration.

If the keystore is unavailable, the app runs unencrypted and says so plainly
in Settings. A user locked out of their own training log is a worse outcome
than an unencrypted cache on a device that already cannot keep a secret.

## 8. Sync

`SyncEngine` drains the outbox on connectivity regain, on a five-minute tick,
and on demand. Failures back off exponentially to a fifteen-minute cap; after
ten attempts an entry is **parked** and surfaced in the UI, because silently
discarding a logged workout is the worst failure this app has.

Conflict resolution is last-write-wins on `updatedAt`, and a pull never
overwrites a local record that is strictly newer — otherwise a slow pull could
undo something the user typed thirty seconds ago.

## 9. Firebase, and life without it

`FirebaseConfig` reads its options from `--dart-define` values. Nothing is
committed. When they are absent, `FirebaseService` reports
`FirebaseStatus.notConfigured` and the app enters **local mode**: a
device-local session, no replication, every feature working. The welcome
screen offers it as a first-class choice.

This is what makes the app testable end to end without a project, and it is
why the entire test suite runs in the same configuration a user would have on
day one.

## 11. Deliberate non-goals in the MVP

No Cloud Functions. Every engine runs on the device: the calculations are pure
functions over one user's own data, they must work with no signal, and a
server round-trip would make them slower and less available without making
them more correct. `functions/` retains the TypeScript mirror for the parity
gate and ships when there is a job only a server can do.

No Firebase Storage. Progress photos — the most sensitive data in the product
— stay in the app's private directory. Not uploading them is a stronger
guarantee than any rule.
