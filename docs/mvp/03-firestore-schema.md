# 03 — Firestore schema

## 1. Shape

Everything a user owns lives under their own document. There is no path where
one user's query can reach another's data, and ownership is a single
comparison in the rules.

```
users/{uid}                                the profile document
├── settings/preferences                   exactly one document
├── foods/{foodId}
├── meals/{mealId}
├── nutrition_logs/{logId}                 food AND water entries
├── supplements/{supplementId}
├── supplement_logs/{supplementId}_{date}  deterministic id ⇒ idempotent
├── exercises/{exerciseId}
├── workouts/{workoutId}                   programs
├── workout_sessions/{sessionId}           sets nested inside
├── body_measurements/{measurementId}
├── tasks/{taskId}
├── calendar_events/{eventId}
└── notifications/{reminderId}             user-created daily reminders
```

Thirteen sub-collections plus the user document. Two rules govern the shape:

**Ids are generated by the client.** That is what makes an offline write
idempotent — replaying it is a `set(merge: true)` to the same path, not a
second insert.

**Nothing derived is stored.** No `daily_totals`, no `personal_records`, no
`analytics` collection. Personal records are recomputed from sessions;
macro targets are recomputed from the profile. A derived value in the database
is a value that can disagree with the thing it was derived from.

## 2. Field types

Every document carries:

| Field | Type | Meaning |
|---|---|---|
| `id` | string | equals the document id (rules enforce it) |
| `updatedAt` | **ISO-8601 string** | conflict resolution; last write wins |
| `deletedAt` | ISO-8601 string or null | tombstone |

`updatedAt` is a string, not a Firestore `Timestamp`. The offline write path
serialises the entity to JSON for Hive and replays *the identical map* to
Firestore, so the two stores can never disagree about a type. A rules file
that demanded `is timestamp` would reject every write this client makes —
which is exactly what the original design did, and what the rules test suite
caught.

## 3. Collections in detail

### `users/{uid}`

```jsonc
{
  "id": "uid",
  "email": "sam@example.com",     // empty string in local mode — no fake address
  "displayName": "Sam",
  "photoUrl": null,
  "dateOfBirth": "2000-05-04T00:00:00.000Z",
  "sex": "male|female|unspecified",
  "heightCm": 180.0,
  "weightKg": 82.0,
  "activityLevel": "sedentary|light|moderate|active|very_active",
  "goalMode": "cut|maintain|bulk",
  "trainingDaysPerWeek": 4,
  "targetWeightKg": 78.0,
  "leanMassKg": null,
  "weeklyRateTargetPct": 0.5,
  "onboardingCompletedAt": "2026-03-14T09:00:00.000Z",
  "targetsOverridden": false,
  "overrideKcal": null, "overrideProteinG": null,
  "overrideCarbsG": null, "overrideFatG": null, "overrideWaterMl": null,
  "createdAt": "...", "updatedAt": "...", "deletedAt": null
}
```

Targets are **derived** from this document by `MacroCalculator`, never stored,
unless the user explicitly overrides them (`targetsOverridden`). Editing a
bodyweight therefore cannot leave a stale calorie goal behind.

### `nutrition_logs/{logId}`

Food and water share one collection, discriminated by `type`. That is
deliberate: a day's totals are then one pass over one collection rather than a
join across two.

```jsonc
{
  "id": "uuid-v4",
  "type": "food|water",
  "foodId": "…", "foodName": "Chicken breast (Tesco)",
  "grams": 200.0, "quantity": 200.0, "unit": "g|ml|serving",
  "macros": { "kcal": 330, "proteinG": 62, "carbsG": 0, "fatG": 7.2 },
  "slot": "breakfast|lunch|pre_workout|post_workout|dinner|before_bed|snack",
  "mealId": null,
  "waterMl": 0,
  "loggedAt": "…", "localDate": "2026-03-14",
  "updatedAt": "…", "deletedAt": null
}
```

`macros` is denormalised onto the log **on purpose**. It is the one place this
schema duplicates data, and the reason is correctness: a log records what was
eaten at that moment. Editing the food's nutrition later must not silently
rewrite last month's history.

`localDate` is the user's calendar day as a string. Grouping by a UTC
timestamp puts a 23:30 meal on the wrong day for most of the world.

### `supplement_logs/{supplementId}_{localDate}`

The document id is deterministic. Tapping "taken" in the app after acting on
the notification records **one** dose, not two — idempotency by construction
rather than by a check that can be raced.

### `workout_sessions/{sessionId}`

Sets are nested inside the session rather than stored as their own collection.
A session is read and written as a unit, is bounded (a long session is a few
dozen sets, far inside the 1 MiB document limit), and the live screen updates
it many times per minute. A sub-collection would turn one write into forty.

```jsonc
{
  "id": "uuid", "workoutId": "…", "name": "Push A",
  "plan": [ { "exerciseId": "…", "targetSets": 3, "repMin": 6, "repMax": 8,
              "restSeconds": 150 } ],
  "sets": [ { "id": "…", "exerciseId": "…", "weightKg": 100, "reps": 5,
              "rpe": 8, "isWarmup": false, "performedAt": "…",
              "prLabels": ["Best e1RM"] } ],
  "startedAt": "…", "finishedAt": "…",
  "status": "in_progress|completed|abandoned",
  "localDate": "2026-03-14", "notes": null,
  "updatedAt": "…", "deletedAt": null
}
```

### `notifications/{reminderId}`

User-created daily reminders — the "remind me to weigh in at 07:00" case that
has nowhere else to live. Named `notifications` to match the agreed schema.

```jsonc
{ "id": "uuid", "title": "Weigh in", "note": "Before breakfast",
  "hour": 7, "minute": 0, "enabled": true,
  "createdAt": "…", "updatedAt": "…", "deletedAt": null }
```

### `settings/preferences`

One document. Four fields, each of which changes behaviour when it moves:
`theme`, `remindersEnabled`, `analyticsConsent`, `crashReportsConsent`.

## 4. The collection that is deliberately absent

The agreed schema listed an `analytics` collection. It is **not** created, and
that is a decision rather than an omission:

- Firebase Analytics already is the analytics store. A Firestore mirror would
  duplicate data the schema rules explicitly forbid duplicating.
- Nothing in the MVP reads it. A collection nothing reads is a collection that
  silently rots.
- The aggregates it would hold (daily totals, weekly volume) are derived from
  at most a few thousand local records in single-digit milliseconds. Caching
  them would create exactly the derived-data disagreement this schema avoids.

It ships when a cross-user aggregate exists that only a server can compute.
See `docs/mvp/14-technical-debt.md`, entry TD-07.

## 5. Indexing strategy

**No composite indexes.** Every query the client makes is:

```dart
collection.orderBy('updatedAt', descending: true).limit(500)
collection.where('updatedAt', isGreaterThan: since)
          .orderBy('updatedAt', descending: true).limit(500)
```

A range and an order on the *same* field are served by Firestore's automatic
single-field index. There is nothing to declare, and no query that will fail
in production with a console link nobody clicks.

The reason the query surface is this small is architectural: **the UI never
queries Firestore.** Reads come from Hive. Firestore is a replication target
and a second device's inbox, so the only query it ever needs to serve is
"what changed since I last looked?".

**32 field exemptions.** Firestore indexes every field of every document by
default, ascending, descending, and array-contains. For fields no query ever
touches that is pure write amplification and storage cost. `firestore.indexes.json`
disables indexing for free text and nested arrays:

| Collection | Exempted fields |
|---|---|
| `foods` | name, brand, servingLabel |
| `meals` | name, items |
| `nutrition_logs` | foodName, macros, slot |
| `supplements` | name, notes, dose, weekdays |
| `supplement_logs` | supplementName |
| `exercises` | name, notes |
| `workouts` | name, notes, plan |
| `workout_sessions` | name, notes, exercises |
| `body_measurements` | notes, photoPath |
| `tasks` | title, notes |
| `calendar_events` | title, description, location, providerEventId |
| `notifications` | title, note |
| `settings` | theme |

At 10 000 users this is the difference between a few gigabytes of index and a
few hundred megabytes, and it removes three index writes per document write on
the hottest collections.

## 6. Cost model at 10 000 users

Per active user per day, assuming a heavy user: 6 meals, 2 water logs, 4
supplement doses, 1 workout with 25 sets, 1 body measurement, 3 task edits.

| Operation | Per user/day | 10 000 users/day |
|---|---|---|
| Document writes | ~45 | 450 000 |
| Document reads | ~30 (delta pulls only) | 300 000 |
| Deletes | 0 (tombstones are writes) | 0 |

Reads are low precisely because the UI reads Hive. The dominant cost is
writes, and the live workout screen is the spike — 25 set writes in an hour.
That is already collapsed by the outbox, which keys pending entries by
`collection/docId`, so rapid edits to one session become one network write
rather than one per set.

Storage per user after a year is on the order of 15–40 MB, dominated by
`workout_sessions` and `nutrition_logs`. Progress photos are not included
because they never leave the device.
